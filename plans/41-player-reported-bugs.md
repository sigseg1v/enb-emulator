| PB-2 | `[~]` | **Can't fly with normal thrusters -- client shows you moving but server position diverges; spacebar/autopilot/warp snap you back to the real (server) position; stuck on planets where you can't warp.** | Reported 2026-06-01. ROOT CAUSE (corrected): our proxy has NEVER fed client position to the server. `proxy/UDPProxyMVAS.cpp` (which streamed `0x1004` to MVAS port 3806) existed but was already inert in the proxy build -- its position source `engine_read_process` was a `return false` stub in `proxy/Net7.cpp:288`; the only real cross-process scrape lived in `launcher/SocketTest.cpp` (the old Win32 launcher, a separate binary, not how players run today). That dormant file was then deleted in `4dc71638` (Phase AA consolidation). So this is NOT a simple "port" -- there is no working feed to restore; a NEW position source is required. The server only gets thrust-impulse `0x0014 MOVE` (no coords) and dead-reckons via `CalcNewPosition`, so it diverges; autopilot/warp are server-driven (explicit `SetPosition` + `SendLocationAndSpeed(true)`) so they re-sync. PRIMARY SOURCE: live Net7Proxy capture `proxy/local-debug/Combat-...-20260604-072157.pcapng` -- `0x1004` to udp/3806 x196 during thrust (the real proxy streamed it densely). FIX (in-client hook, loopback-datagram transport): an in-client Detours hook (`client/detours/ClientPositionFeed.{h,cpp}`) reads the engine ship state in-process and sends it to the proxy as a fixed 40-byte UDP datagram on loopback port `NET7_CLIENT_POS_PORT`=3807 (`proxy/ClientPositionShared.h`); the proxy consumer (`UDPClient::ReadClientShipPosition` -> `SendPositionIfChanged`, `proxy/UDPClient_linux.cpp`) binds 3807, drains the latest sample (latest-wins, 1.5s staleness gate), and streams `0x1004` to 3806, change-gated. **Transport was changed from named shared memory to a loopback datagram (2026-06-08)** because the SHM design structurally could NOT reach `just play-local`: there the proxy is a Linux docker process and the WINE client's Win32 named mapping is invisible to it. A loopback datagram is the ONE transport that works in all three run modes -- play-local (WINE client -> docker proxy, port published `127.0.0.1:3807:3807/udp`, loopback-only), play-online/NET7MP (WINE client -> WINE proxy), and native Win32. The proxy binds 127.0.0.1 on the Win32 build and INADDR_ANY on the docker build (host publish loopback-restricted). NO server change and NO `0x1004` wire change -- the server still consumes 0x1004 over its authenticated DTLS channel exactly as before; the position the proxy attributes is its own session's `m_PlayerID`, so a loopback feed only ever moves the feeder's own avatar (no new server trust boundary). `0x1004` wire shape still pinned by `CaptureReplayTests.MvasPosition_1004_*` (fixture `live_mvas_position_1004.hex`). DLL INJECTION (now wired, 2026-06-08): the feed ships as a minimal standalone 32-bit DLL `bin/FreyaPosFeed.dll` (`client/detours/PosFeedDllMain.cpp` guarded `DllMain` -> `Net7ClientPosFeed_Start`, only inside `client.exe`) built via `just build-posfeed-dll` (needs the **i686** MinGW toolchain -- `sudo apt install gcc-mingw-w64-i686-posix g++-mingw-w64-i686-posix` -- because `client.exe` is PE32/i386 and the injected DLL must match its bitness; the 64-bit MinGW used for the proxy cannot emit it). It is deliberately NOT the legacy `ClientDetours.dll` (that links MSVC `detours.lib` mingw can't link, and hooks hardcoded client offsets specific to one build). Injection under WINE is a launch-time remote-thread inject, NOT `AppInit_DLLs`: WINE (tested wine-11.8) does not implement the `AppInit_DLLs` loader hook at all, so registering the DLL there loads it into nothing (proven empirically -- it injected into neither `client.exe` nor `notepad`). Instead a tiny 32-bit MinGW injector `bin/FreyaInject.exe` (`client/detours/FreyaInject.cpp`, built alongside the DLL by `just build-posfeed-dll`) does the classic `CreateProcess(CREATE_SUSPENDED)` + `VirtualAllocEx`/`WriteProcessMemory`(dll path) + `CreateRemoteThread(LoadLibraryA)` + `ResumeThread`; on any failure it `TerminateProcess`es the child so a half-injected client never reaches the user. The launcher (`tools/LaunchFreya` `Launcher.ConfigurePositionFeedInjection`, gated on the `EnablePositionFeed` setting; `play-local` sets it true and builds the DLL+injector as a required step) stages the 32-bit DLL into BOTH `system32` and `syswow64` (WOW64 file redirection sends a 32-bit process opening `system32` to `syswow64` on a win64 prefix), then `LaunchClient` spawns `wine FreyaInject.exe <client.exe DOS path> <FreyaPosFeed.dll DOS path> -SERVER_ADDR ... -PROTOCOL TCP` instead of launching `client.exe` directly. `DllMain` emits an `OutputDebugStringA` marker on attach so injection is observable even while the feed is inert (definitive load check is `WINEDEBUG=+loaddll`). Native-Windows injection (Detours withdll) is NOT wired -- WINE path only. REMAINING BLOCKER: the engine read itself (`ReadEngineShipState`, owner seam, returns false until filled) + real-client confirmation -- tracked as CV-MVAS-POS in `plans/29`. The seam loads its build-specific read from a gitignored local header: copy `client/detours/ClientEngineOffsets.local.h.example` to `ClientEngineOffsets.local.h` and fill `Net7ReadEngineShipState_Local()`; `ClientPositionFeed.cpp` includes it via `__has_include` (absent -> feed stays inert, the committed default). This keeps client addresses/layout structurally out of version control. Both proxy build targets (Linux-native docker + Win32 mingw cross) compile green with the new consumer; the producer compiles clean under mingw. Same subsystem noted in `plans/27 §"Why it broke"`. |
| PB-1 | `[x]` | **Credits underflowed to ~270 billion, change on every login.** | Fixed 2026-06-01, commit `421cd9bd` (local). `Player::SaveCreditLevel` wrote a u64 credits value through the 4-byte `AddData<unsigned long>` specialization (on Linux `u64 == unsigned long`), so the SaveManager 8-byte read pulled an uninitialized high dword.
