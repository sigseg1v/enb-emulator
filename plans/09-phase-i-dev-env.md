- [x] **Shard the `cli-integration-test` CI job to stop it timing out** (owner-requested 2026-06-03, task #63). The xUnit integration suite (~355 tests) cannot parallelise in-process -- one shared `ServerCollection` / one docker-compose stack / single-client proxy -- so the single job ran fully serial at ~24 min of tests + ~3 min bring-up and kept blowing past even the 45 min timeout. Split it into a 3-way `strategy.matrix` (`shard: [1,2,3]`), each shard a parallel job with its OWN compose stack running a disjoint ~1/3 slice (timeout dropped to 25 min/shard). The slice is computed at runtime from `dotnet test --list-tests` by `tools/ci/integration_shard_filter.py` (greedy longest-processing-time over METHOD-level granularity -- one class, `SectorChatTests`, is ~176 [Fact]s = half the suite, so a class-level split could not balance it). No hardcoded test names anywhere: a newly added test is discovered and auto-assigned, per the owner's "catchall that automatically includes new tests" requirement. A separate fast (no-docker) `cli-integration-coverage` guard job runs the partitioner's `--check`, which fails CI if any method is unassigned, double-assigned, or (for the lone [Theory]) prefix-overlaps another -- so sharding can never silently drop a test. Match terms: exact `FullyQualifiedName=` for [Fact]s (no prefix collision); contains `~` for [Theory] methods (a literal `(` cannot be used -- VSTest parses it as a filter grouping operator and it nukes the whole expression; the prefix-guard covers the collision risk instead). The C++ proxy<->MVAS ctest smoke is gated to shard 1 only (it is not a function of the test slice). Verified locally against real `--list-tests`: shards select 119/118/118 = 355 with zero overlap and zero drop; `--check` green.
